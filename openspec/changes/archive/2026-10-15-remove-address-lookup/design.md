# Design

## Context

`PropertyForm.svelte` (used by `/admin/properties/add` and `/admin/properties/[propertyId]/edit`) loads the Maps JavaScript API through `src/lib/google.ts`, which wraps the `google-maps` npm loader and passes it `PUBLIC_FB_API_KEY`. In `onMount` it attaches the legacy `google.maps.places.Autocomplete` to an unnamed "Address Lookup" input. A `place_changed` handler then fills `streetAddress`, `city`, `state` and `zip` in the superform store. Nothing else imports `$lib/google`. Several e2e specs abort `**/maps.googleapis.com/**` so the form doesn't reach the network.

The investigation in `lifecycle.md` shows why the lookup is broken. See proposal.md (Why) for why it is being removed instead of fixed.

## Goals / Non-Goals

**Goals:**
- Leave a form with no dead code paths: no Maps types, no `onMount` loader, no unused imports.
- Keep the remaining form, its validation and its submit behavior byte-for-byte the same.

**Non-Goals:**
- A feature flag or provider abstraction for a future lookup.
- Changes to the Google Cloud projects or to `PUBLIC_FB_API_KEY`.

## Decisions

- **Delete instead of hiding behind a flag.** The lookup is rarely used and is broken today. A flag would keep an unmaintained dependency and Maps typings around for nothing. Bringing it back later is a fresh change against Places API (New) or another provider, so keeping the legacy code would not save any work.
- **Remove the e2e route stubs and assert that nothing calls Maps.** The stubs were there only to keep e2e off the network. Once they are gone, a call to Maps that comes back would fail without a clear signal. One check in `property.spec.ts` that records requests to `maps.googleapis.com` on the add and edit pages turns the spec's "no third-party lookup requests" scenario into a test. The other specs simply drop their stubs.
- **Keep the "Address" heading.** It still groups the address fields. Only the lookup's label and input go.
- **Remove `google-maps` with `npm uninstall`** so `package-lock.json` is regenerated by npm, not edited by hand. The deprecated `@types/googlemaps` comes in only as a dependency of `google-maps` and leaves with it.

## Risks / Trade-offs

- [An admin used the lookup to get the zip+4 or exact street spelling] → Low impact: the lookup has been broken, so admins already type addresses by hand. Validation is unchanged.
- [Something else on the page relied on the global `google` object] → `$lib/google` has a single importer. Confirm with a repo-wide search and `npm run check` after removal.
